# Hoopa Constitution

## Core Principles

本文的“必须”与“禁止”分别表示 MUST 与 MUST NOT。原则约束产品行为与验收，
不表示相关能力已实现；未取得运行证据的能力必须标明未验证。

### I. CLI 优先与独立转发

Hoopa 必须保持面向 Linux SSH、日常终端和 Agent 工作流的 CLI-first Proxy Manager 定位。
核心操作必须可通过非交互 CLI 完成；按需 TUI 必须复用相同用例，退出界面不得等同停止代理。
基础管理与不计量接入必须能在没有 GOST、SQLite 数据库和 TUI 的环境工作。

Mihomo 必须作为独立代理与路由核心运行；Hoopa 禁止自研代理协议内核。
管理面与转发面必须分离，已应用策略的逐连接执行不得以界面或管理器在线 RPC 为前提。
管理器崩溃后的转发连续性、进程存活与重启接管必须通过原型验收后才能对外承诺。

### II. 本地策略权威与确定性选路

订阅必须只提供节点，规则、稳定逻辑组及跟随关系由本地掌握；US、JP、BEST 等逻辑名称
不得随供应商显示名变化。应用、进程、域名和 IP 规则必须遵循公开、确定的顺序，
按第一条确定匹配执行，禁止隐式重排为“更具体自动优先”。

应用和经过验证的真实源进程规则必须能够指向逻辑 group 或固定节点。
固定节点必须绑定来源与稳定节点身份，不得随活动订阅切换重绑定为同名节点；
完整候选必须校验所有被引用来源。规则所需身份不可判定时必须显式拒绝相关连接，
不能将未知当作不匹配继续落到其他目标。

缺失组、节点、必需候选或匹配能力时必须拒绝变更，保留上一份可用快照。
禁止因缺节点、目标不可达或更新失败而悄悄直连、换供应商或解除固定选择；
用户明确配置的直连规则与自动组候选内选优不属于隐式后备。

### III. 可恢复变更与可靠进程身份

配置修改必须先准备和校验完整候选，串行应用运行状态变更，保存可恢复的操作身份、
配置世代与阶段，并在核验实际运行态后发布成功。文件替换、多个核心 API 调用与数据库事务
必须分别描述边界，禁止将它们宣称为一个跨资源原子事务。

失败必须恢复并验证完整旧快照后才能报告回滚成功；回滚失败或运行状态无法判定时，
必须保留证据、显示 degraded 并停止自动写操作，不得假报恢复或改为直连。
进程接管和停止必须校验 PID 以外的启动身份与实例归属，禁止误杀或接管外部进程。

小时级更新必须有界执行、失败保留快照；休眠恢复后每个到期订阅至多补一次更新，
禁止重放积压周期。需要中断连接的变更必须暴露影响，并遵循显式应用或预先配置的中断策略。
现有长连接是否中断或保留旧路径必须说明，禁止承诺未经验证的连接迁移。

### IV. 局部接入与版本化集成

managed、inherit、direct 必须只作用于目标子进程；禁止暗改父 shell、系统代理或应用持久配置。
managed 入口不可用时必须明确失败，不得静默降为 inherit/direct；direct 不承诺绕过已有 TUN、
VPN 或应用自身代理。进程规则只约束已进入 Hoopa 的连接，不得声称按名称自动捕获整机流量。
应用启动必须使用参数数组，并保留信号、终端中断与目标退出状态的语义。

固定版本安装职责归 Rotom；Hoopa 必须消费明确的外部核心路径、版本与能力，
不得在运行中自动替换或升级核心。agentcfg 等调用方必须通过版本化 JSON 接口集成，
禁止直接读写内部配置或数据库。机器响应必须保持结构稳定，stdout 不混入进度、
交互提示或子进程输出；管理协议与应用执行输出必须分开。

### V. 同源计量与完整原始事实

计量必须限定为 Hoopa 计量入口的已验证流量，不能称为模型 Token、供应商账单或整机审计。
范围内必须保留入口字节事实及可核验的进程、域名归属；真实源进程必须包含 PID、进程名与
启动身份，不能用 GOST、launcher 或可复用 PID 冒充。短连接、退出进程和子进程的历史必须
按承诺的保留范围可查。域名必须来自可关联的实际证据，不能根据共享 IP 或当前 DNS 猜补历史。

原始记录必须关联服务身份、运行世代和计数世代；checkpoint 与对应增量必须同事务提交，
稳定样本身份必须防止重试重计。入口总量、进程、同名组、域名和交叉视图必须从同源事实投影，
同名合并只能改变查询展示，不能销毁实例记录或重复累加。必须支持时间筛选、排序和下钻，
分页与 Top N 不得丢失隐藏项和未知项的总计。

对账必须核对方向、计数边界、世代与截止点；不同口径禁止硬凑相等或按比例摊分。
未知字节、进程未知、域名未知、协议开销与采集缺口必须分别表达，不能伪装成零。
受控支持场景必须证明真实归属和完整采集，不能以全部标 unknown 逃避验收；
仅恢复入口总量不能冒充已经恢复维度明细、逐秒速率或质量历史。

### VI. 可解释的连接质量与只读查询

进程和域名视图必须能够关联实际连接节点、来源、逻辑组、规则及代理链证据；
规则意图、当前 group 选择与历史实际路径必须分开，禁止用当前 now 回填旧连接。
多节点使用必须能下钻到实际连接与节点分布。

节点 probe、转发建立耗时与可见业务首字节必须区分测量定义、范围、目标、单位和来源；
不可见阶段必须显示 N/A。窗口字节量与 B/s 速率必须注明窗口、覆盖和新鲜度，禁止补造缺口曲线。
延迟分布必须保留样本数、失败与超时；禁止平均 p95、混合不可比样本，或把低延迟等同业务成功。

status、doctor、预览和查询必须只读：不得启动服务、创建状态、更新订阅、选优、联网测速、
迁移、修复或自动恢复。主动网络操作必须明确分离；不能因使用 HTTP GET 就认定无副作用，
也不能为纯测量调用会清除固定选择或改路的接口。证据不足必须如实报告。

### VII. 原型优先与证据驱动交付

工程必须按 P0 组合原型、P1 独立基础管理、P2 可靠计量与交互、P3 平台验收与迁移推进。
P0 必须先证明真实应用链路、计数与连接边界、配置部分失败回滚、管理器崩溃与接管、
采集降级，并验证源身份、短连接、质量计时、实际链及应用/进程选路的可行性。
关键前提不成立时必须调整方案，禁止堆叠完整 CLI/TUI 或降低需求来绕过门槛。

应用 profile 指定组/节点属于 P1；完整历史、进程/域名视图、真实进程规则、同名合并、
排序、质量视图与按需 TUI 属于 P2。基础管理完成不得宣称整个项目完成。
资料阅读、mock、交叉编译和真实平台执行必须分别记录；未执行、环境不足或失败均不得记为通过。

### VIII. 最小权限与可复现工程

本地代理、控制面、metrics 和 IPC 必须采用明确的本地访问范围与私有保护，
不能仅依赖端口隐蔽。loopback、profile 与专属入口不得被宣称为同用户下的 OS 安全隔离。
目录和凭据必须限制权限；订阅秘密、节点认证、controller secret、应用正文和完整敏感环境
不得进入默认日志、JSON、诊断包或 Git fixtures。远端订阅不得覆盖本地监听、规则、路径或脚本。

依赖与核心必须固定版本并记录摘要、来源和能力；发行必须保留依赖许可与版权记录。
Git 保存源码、文档、测试材料和构建定义，不提交核心可执行文件、发行包、运行账本或真实凭据。
未核对许可和发行义务不得直接复制上游实现；阅读开源产品不等于继承其保证。

### IX. 简洁实现与职责明确的协作

实现必须遵循已存在的真实边界，小接口放在消费方；禁止预建没有需求的插件框架、事件总线、
多内核抽象或空包。CLI/TUI 必须调用同一业务用例；纯策略不得依赖 UI、GOST 或 SQL。
验证必须针对风险与受影响路径，新增证据才能推动扩大审查，不能反复重跑无关全量检查。

简单单步任务直接完成；适合独立拆分的工作必须遵循适用的 AGENTS 与会话协作规则主动委派。
主代理沿用会话模型与 effort，负责需求、取舍、
事务/锁/恢复语义和最终验收；executor 与 scout 按各自角色配置执行实现或收证。
同时最多两个子任务，子代理不再派生；每个任务包必须声明目标、输入、独占可写范围、
接口/不变量、验收命令与升级条件，并保留他人改动。主代理不得重复已委派工作。

子代理必须完成分配范围内的验证和常规修复后交接；前提失败、范围扩大、语义不明或
同一失败经两种有效尝试仍未解决时必须升级主代理。最终审查必须针对写入完成的稳定内容。
任务记录必须区分已完成、进行中、失败待决策、环境不足未验证，并报告实际执行模型与证据；
命令限制写入范围时，必须使用允许的报告或交接记录，不能为记日志额外修改文件。
用户当前明确指定模型、禁止委派或已有授权必须优先，不得增加重复的确认或“继续”步骤。

## 技术与产品边界

- 项目名 Hoopa，命令 hoopa，展示说明 CLI-first Proxy Manager；仓库后缀未定，不得臆定发布地址。
- 使用 Go + Cobra；Bubble Tea / Bubbles 按需提供 TUI；Mihomo 独立运行，GOST 为可选计量入口，
  SQLite 用于检查点与历史账本。SQLite 驱动和进程托管方案必须经原型验证并以 ADR 定稿，
  不在宪章锁死具体实现。
- 采用单仓库、单 Go module，构建生成一个 hoopa 程序；具体包目录按实现需要建立。
- 禁止默认启用 TUN、系统全局代理、自启动、系统计划任务、特权采集或业务解密。
  不建设 Web 管理平台、云同步、远程控制平台和插件市场。
- Linux 优先实际验收；macOS/Windows 只能在不额外收费的标准托管 CI/可用额度内执行适用验证。
  退出、休眠与恢复必须另有实际环境证据，未经验证的平台不得宣称正式支持。
- 性能预算为待测目标：管理器空闲 RSS ≤40 MiB，10 分钟平均 CPU <单核 0.5%，整套空闲内存
  ≤200 MiB；Hoopa 发行压缩包 ≤10 MiB、二进制 ≤25 MiB。测量必须声明平台、规模、入口数、
  构建参数及外部核心口径；不得通过丢弃承诺的明细达标，也不得将目标写成实测结果。

## 开发流程与质量门槛

1. spec、plan、tasks 和评审必须列出相关宪章原则、验收证据及未验证假设。
   具体启动顺序、命名入站、计量入口复用、驱动和表结构必须留在设计/ADR，不把候选方案升为事实。
2. 每项变更必须说明触发场景、行为、失败路径、恢复与兼容影响；配置和 API 使用版本化 schema。
   明确的常规实现与可逆修改按既有授权推进，仅缺必要人类决策或授权时询问。
3. 必须执行与变更相称的静态、单元、适配和集成检查；实现存在后完成规定的格式、vet、测试及
   适用 race 检查。进程、事务和恢复语义必须有故障注入与真实链路证据，mock 不能代替。
   文档修改必须检查链接、占位符和空白，不为无代码变更虚构 Go 测试或强制机械 TDD。
4. 关键故障必须覆盖管理器崩溃后转发、重启接管、采集器降级、部分应用与回滚失败；
   新增身份、统计、计时或路由语义必须同步可复现的测试矩阵，环境不足不得阻塞无关工作。
5. P0/P1/P2/P3 的退出条件分别验收；P3 迁移必须可预览、备份和回退，实际替换旧工具需明确执行。
   文档范围命令不得自动进入特性实现、构建、部署或修改依赖模板。

## Governance

本宪章是项目内部规格、计划、任务与实现评审的治理基准。用户当前明确指示与授权范围优先；
冲突必须由主代理记录并协调，禁止以宪章推导出额外写入、部署或外部操作授权。
现有未验证设计被采纳为验收目标，不表示其实现已被证明；未通过的门槛必须继续显式保留。

修订必须记录动机、旧新原则差异、兼容/迁移影响及依据，主代理审核约束是否仍可验收，
再按用户的明确请求或既有授权落盘。原则例外必须有明确授权、范围、理由与后续处理；
实现困难、时间或预算压力不能单独构成降低原则的理由。

版本遵循 MAJOR.MINOR.PATCH：删除或不兼容地重定义原则升 MAJOR；新增原则/章节或实质扩充
治理要求升 MINOR；不改变含义的澄清与排版修正升 PATCH。首次正式采纳为 1.0.0。
采纳日期保留首次日期；仅在宪章内容变更时更新 Last Amended，不以实现版本代替治理版本。

每次规格/计划/任务生成与最终评审必须核对受影响原则，差异须在同一变更内处理或明确列为
尚未解决的治理问题。宪章工作流只修改本文件，依赖模板和命令在运行时读取宪章，
不得为同步而擅自改写模板或启动其他 Spec Kit 命令。
文件顶部 Sync Impact Report 仅供本次审核，提交宪章前必须移除该临时 HTML 注释；
不将其执行状态或模型信息作为长期产品原则。
