# Application launch originals v1

Root T056 codec/ordering decision, 2026-10-29; this is the implementation contract, not runtime acceptance. It refines [application-launch-store-v1](application-launch-store-v1.md) and [application-launch-v1](application-launch-v1.md). It adds no management RPC or traffic identity claim.

## Captured declaration and records

An invocation uses the committed profile whenever an active generation exists; otherwise direct/inherit may use the explicitly initialized draft. Missing/corrupt committed evidence never falls back to a different draft. A draft's profile revision is `draft:<canonical-intent-sha256>`, with nil generation/manifest; a committed profile retains its exact active revision, generation, manifest digest and canonical Intent digest. The captured original App fields are stored in the reservation along with the invocation's selected mode. The selected metering value must be false in this first executable profile; configured/requested metering is rejected before reservation, never silently disabled. Managed requires committed provenance and the exact entry-binding digest. Direct/inherit have no managed binding reference.

The reservation stores the captured App declaration (ID, original mode/metering and bounded bypass tokens), profile commitments, selected mode, entry digest when applicable, and the original wrapper identity. It does not store full Intent, argv, environment, entry credentials or the target executable path. The original App is a local private declaration snapshot, not proof of which process opens later traffic. A later draft replacement cannot change earlier reservation contents.

Every original has schema_version1, exact history ID, exact launch ID and a canonical UTC RFC3339Nano observation timestamp. History/launch IDs use their already defined 24-byte random tokens. The private writer encoding is exact JSON plus LF, rejecting alternate/duplicate/unknown/omitted fields. Digests refer to those exact record bytes. Start ticks use decimal JSON strings. Per-record maximum is64 KiB. Wall time is not required to increase across records, because clock corrections do not change causal ordering.

| File | Required commitments |
| --- | --- |
| `reservation.json` | profile/App/selected mode and original wrapper PID, UID, boot ID, start ticks, PPID, process group and session |
| `birth.json` | reservation digest and original child PID/UID/boot/start/PPID/group/session; child PPID matches the wrapper, child group equals its original PID, boot/session/UID match captured parent |
| `authorization.json` | reservation and birth digests; records durable dispatch intent, not successful delivery of GO or entry into main |
| `terminal.json` | reservation/birth digests, authorization digest or null, exact original wait result, finite actual exec failure if any, finite wrapper failure if any |

Terminal normal exit has exit_code0–255, signal:null and raw wait status exactly exit_code<<8. Signal terminal has exit_code:null, signal1–64 and raw wait status containing that signal and optional kernel core-dump bit only. Nonterminal stopped/continued statuses cannot complete a launch. Actual exec failure requires authorization and a normal launcher exit consistent with the reason: `exec_format`126 (ENOEXEC), `exec_not_found`127 (ENOENT), `exec_permission`126 (EACCES/EPERM), or `exec_unavailable`126 (other failed exec syscall). It is derived from the original anonymous launcher failure channel, never synthesized merely because an app returns126/127. Missing failure evidence stays null; EOF alone is not exec success.

Wrapper failure is independently null or a finite `tty_restore_failed`, `signal_forward_failed`, `launcher_protocol_failed`, or `dispatch_aborted`. Recording the actual root result does not erase a wrapper failure or turn the CLI result into a successful bookkeeping claim. If terminal persistence itself fails, its absence remains unknown and the wrapper reports the already observed root exit/signal with a fixed bounded diagnostic, returning5.

## Allocation and append authority

Allocation takes only the existing allocation lock, with a context-cancellable wait bounded at two seconds even without a caller deadline. All namespace names/types are checked under that lock. Count final and retained staging directories toward4096; visit at most8192 names. Metadata identity/lock files must remain private and exact. Unknown names/types, unsafe children or unreadable inventory fail completely. No entry is silently pruned to make room.

Here namespace-name validation means immediate children of `app-launches`. Retained staging directories are checked for safe directory identity/owner/mode and counted, but their interiors are unaccepted evidence and are not traversed, interpreted, repaired or deleted. They never enter accepted-launch results or regain a spawn ticket. The complete returned inventory covers every accepted final directory; it is not a forensic inventory of every abandoned staging file. Per-launch interior validation below applies to accepted final directories.

A new staging directory holds a private0600 empty `.owner.lock` and the complete reservation. Hold that owner lock before publication; synchronize file and staged directory, publish final directory with Linux no-replace rename, then synchronize namespace. Retain staged/final evidence after any failure. Successful return is the only source of a fresh writer; read originals never construct one. Release allocation lock before spawn or stage append. The fresh writer shares its lifetime/mutex across Go value copies; `TakeSpawn` is consumed once even if the later child start fails. No inherited user application descriptor prolongs the owner lock.

The allocator sets the exact0700/0600 modes only on its freshly exclusive-created directory/file inodes before publication, so a restrictive umask cannot create an unreadable retained entry as an otherwise successful allocation. It does not chmod pre-existing namespaces, originals or unknown names. Reads never change modes. A failed filesystem mode operation still stops publication and retains evidence.

Only that writer can append birth, authorization and terminal once each. Birth requires the consumed spawn ticket; authorization requires successful durable birth; terminal requires birth and matches any recorded authorization. A failed write/publication poisons this writer, preventing additional authorization or bookkeeping based on uncertain state. A caller cannot retry an existing authorization as permission to send another GO. Closing a writer releases only its handles, never kills/adopts an application, deletes records or frees an uncertain lease.

Append uses an exclusive `.tmp-<48 lowerhex>` file, file sync, exact private-file validation, Linux no-replace rename and directory sync. Unpublished temporary files may remain as evidence; they are never interpreted as accepted stages. Readers allow at most16 directory entries per launch, validate metadata and finite temporary-name/type/size shape, and tolerate disappearance only of a recognized temporary during concurrent rename. Unknown names or malformed published originals fail the entire inventory.

Readers snapshot complete final names under a shared allocation lock, then release it before record reads; they never acquire owner locks or perform sync/write/repair. A complete read has an additional64 MiB aggregate accepted-original byte bound and fails wholly when exceeded. For each launch, read terminal first, then authorization, birth and reservation, checking all references. Concurrent append can produce an earlier valid prefix. Missing authorization means `not_authorized`; an original authorization means `authorization_recorded`; a validated terminal exec failure means `exec_failure_reported`. These are evidence states, not inferred root liveness.

The initial view always reports descendants `unknown/not_enumerated`. Direct/inherit lease state is `none`. A managed reservation without authorization remains `reserved`; after authorization or a terminal root result its lease is `unknown`. This initial reader does not claim a live lease is `ready` from old metadata alone. Missing root/terminal fields stay nil. A complete inventory is returned only if every accepted final entry is readable and valid.
