# Subscription scheduling v1

Root implementation decisions, 2026-10-28. T042 implements the bounded in-memory scheduling module; T043 owns the sole service instance, private durable source state, explicit update commands and commit-time identity recheck. No persistence or restart guarantee is inferred from an in-memory test.

The API and initial executable tests are `internal/schedule/update_test.go`: `New(states, now, fetch, validate)`, `RunDue(ctx)`, and `States()`. SourceState carries ID, nullable positive integral UpdateHours, NextDue/LastAttempt/LastSuccess, per-attempt Updating/Downloaded/Validated, latest/pending/applied snapshot IDs and a bounded LastError. Config IDs use the common parser; optional empty snapshot IDs represent absence. New rejects duplicate/invalid source IDs, invalid nonempty snapshot IDs, nil dependencies, zero/overflowing hour durations, unknown error codes, and Updating=true input (an interrupted operation needs explicit higher-layer reconciliation). State copies own their schedule pointers. Construction and getters perform no fetch, validation, timer, filesystem or system task work.

One Scheduler belongs to the single management service. A mutex protects only its states and active-run flag. Fetch, validation and injected clock callbacks run outside this mutex, so readers remain available and callbacks cannot lock out States. Concurrent RunDue returns ErrBusy without invoking callbacks or changing state. At most two workers exist, with each source present once in the fixed work list. The module does not claim global exclusion between separately constructed instances; T043 must not construct competing service schedulers.

Each call captures one wall-clock cutoff and selects enabled sources with zero NextDue or NextDue <= cutoff, preserving input order. It never appends newly due work to this batch. On actual worker start, sample the clock again, set LastAttempt and NextDue=start+period, reset Downloaded/Validated and mark Updating. Long downtime produces one attempt per due source, never one job per missed period. A queued source does not consume its due slot until it starts. Clock rollback before NextDue produces no extra attempt; wall clock values have monotonic data removed. Nil context, zero/out-of-serializable-range time or an overflowing deadline produces a bounded error without manufacturing dates. No constructor-created background loop is added.

Fetch and validation receive the same cancellable context. Successful fetch marks Downloaded, while only a valid snapshot ID from successful validation may update LatestSnapshotID, LastSuccess and PendingSnapshotID. AppliedSnapshotID is never modified; matching the already-applied ID clears pending. Failure retains prior usable, pending and applied IDs and LastSuccess. A failed source does not prevent other eligible sources in the batch from running. Overall failure returns ErrUpdateFailed without callback error text. LastError is only fetch_failed, validation_failed or cancelled (empty means no recorded error). Cancellation/deadline errors preserve errors.Is for the context cause, including a context error returned by a callback; arbitrary callback error chains are not exposed.

Cancellation stops dequeueing unstarted sources, passes through to started callbacks, and joins both workers before releasing active-run ownership. A callback returning success after the context has been cancelled must not publish a new candidate. Updating is cleared only after the original callback returns. Callbacks must honor context; the module cannot safely terminate an arbitrary Go function. Unstarted sources retain their complete previous state and remain due. A pre-cancelled call performs no clock/fetch/validation work.

Nil context or an invalid initial cutoff returns ErrInvalidSchedule before work. Invalid worker-start/deadline keeps that source unchanged and joins ErrInvalidSchedule with ErrUpdateFailed. Invalid completion time after a valid attempt preserves Downloaded and old snapshot IDs/LastSuccess, leaves Validated false, and records validation_failed with the same two error classes. A callback's own context.Canceled/DeadlineExceeded only fails that source when the parent context remains live; other due sources continue. Parent cancellation takes precedence over sampling completion time. Fetch success observed only after cancellation does not advance Downloaded or enter validation; this flag describes an accepted stage completion, not whether any network bytes arrived.

The module has no Apply hook and cannot interrupt connections. Per-attempt Downloaded/Validated flags do not replace immutable snapshots or prove a candidate exists durably. T043 must persist an attempt reservation before external work, so a service crash cannot repeatedly replay the same due slot; a crash can consume an attempted interval without completing it and must be reported as interrupted. It must write validated immutable assets before publishing latest/pending references, keep active revision unchanged on download, and recheck the source definition/secret input identity and the reservation's original state before publication. A stale completion cannot overwrite newer state. Exact filesystem records and recovery transitions belong in the T043 integration contract before that implementation begins; these obligations are not marked complete by T042.

## Durable service integration decisions

Only subscription definitions in the committed active Intent may enable automatic updates. Optional uncommitted Intent supplied to an explicit update cannot enable a timer. The service adapter uses one fixed wall-clock cutoff per pulse and the same pure due-selection rule as T042; it must not wrap the asynchronous updater with a second in-memory attempt/latest authority. The existing SourceUpdater remains the sole owner of the shared global-two/per-source-one worker limit and Journal reservation.

For an enabled source with no prior attempt, scheduling is due immediately. If a prior attempt has null next_due, its original started_at plus the currently committed period is the effective due time, so an intervening manual acquisition does not cause an immediate duplicate download. This derived time is exposed separately as effective_next_due in subscription.list; next_due retains the original immutable reservation (possibly null). Otherwise the last accepted immutable context's next_due remains the due time even when a later committed Intent changes the interval or source definition. Disabling stops selection immediately; re-enabling preserves an existing due time. The next accepted attempt reserves start plus the currently committed interval. Historical context times are never rewritten, and a large elapsed gap yields one new attempt rather than one per missed period.

The adapter must recheck due eligibility and the exact last-attempt identity inside the updater's admission lock. A pulse snapshot alone is insufficient: an intervening manual update may already have consumed that interval. If revision, period, source definition, previous attempt or worker availability changed, it must admit nothing and leave the next pulse to observe the new state. An unfinished operation left by a dead writer is never replayed, recovered or replaced by the scheduler. It remains visible for explicit recovery.

The service loop is an in-process timer tied to the explicitly started management service, never an OS scheduled task or auto-start service. Cancellation joins it before releasing writer ownership. Status/list remain read-only and do not start the loop. T043 implements the loop and durable adapter; scoped validation is recorded in docs/validation/us3-source-update.md. Controlled-clock catch-up tests and actual service pulse/restart are separate evidence; neither proves physical machine suspend or the full T044 routing matrix.
