# Subscription update and local compilation v1

Root integration decisions, 2026-10-28. This contract defines T043 work; implementation and bounded acceptance are recorded in docs/validation/us3-source-update.md, not inferred from the design text alone. T042 is the bounded in-memory scheduler. T043 adds durable source candidates and real service entry points without creating a second runtime apply state machine.

## Authority and bootstrap

The active pointer and verified complete bundle remain the sole runtime configuration authority. A source update never changes either. `subscription.update` consumes the selected source definition from the committed Intent, or from an optional caller-supplied strict Intent. The latter permits importing a first/new subscription before its nodes can be compiled into a runnable configuration; it does not save a draft or publish runtime intent. A source ID is never inferred from a provider display name. Private source settings supply the existing 32-byte identity key and shared-entry/controller settings; missing settings are an explicit dependency failure, not permission to generate replacement identities during a query or Plan.

The first settings installation is an explicit local initialization primitive for the later T054 CLI; T043 fixtures may invoke that real primitive. It writes a single bounded immutable private record and accepts an identical retry. Different bytes at the same installation identity are a conflict; lost keys are not silently regenerated. This does not publish an active configuration, fetch a subscription, bind a port or start a core. Its fixed schema and history checks are specified below. Human `config plan/apply` remains T139; the T043 control use case and subscription CLI must use the same existing US5 application path.

The implemented private settings codec uses exact JSON bytes with fields `schema_version` (literal1), `identity_key` (base64 of exactly32 supplied bytes) and `runtime` (`controller`, `secret`, complete `sourceprofile.Entry`). It reuses the finite profile validator on an in-memory reject-only configuration to validate credentials/endpoints; it performs no IO or random generation. Getter copies are detached and formatted values redact private material. These settings live at `credentials/source-settings-v1.json`; the opaque Store API alone cannot establish initialization history.

`Coordinator.InitializeSourceSettings` is the explicit local admission boundary. It holds the existing coordinator lock, checks the expected revision and typed settings, and only resyncs an existing identical valid record. For a missing record it requires no published runtime generation/operation, stopped intent, no unfinished journal operation, no source/config/runtime-start/stop history (including compacted identities), and no source assets or staging artifacts. Unrelated terminal service-stop history is allowed. Readers do not call this initializer. Missing keys with observable source history produce recovery-required; the code does not claim to detect a same-UID actor erasing all settings and all independent history simultaneously. The future init command must use this boundary and never call the opaque Store publisher as an automatic repair.

The optional update fields are `intent` and `region_rules` (complete ordered local prefix/region declarations). Human update exposes `--input PATH` and `--regions PATH`; CLI reads those bounded local documents before sending the same service use case. Omitted region rules reuse the last verified explicit policy for that source/key, or the empty policy for a new source; they never guess a country from provider names. The durable original update request binds that policy, allowing RestoreAsset to use trusted local ParseOptions instead of trusting the asset's own region metadata. Exact API/CLI parameter validation and fixtures must include these optional fields before dispatch is enabled.

## Immutable assets and restart-safe identity

F08 treats a downloaded provider with zero nodes as an unusable update. The parser may represent an empty Snapshot for structural tooling, but the persistent updater must record downloaded=true, validated=false, reason=validation_failed and retain the previous committed source Latest. It publishes no empty provider candidate and never changes the active bundle. Plan, list and explicit source recovery also refuse a historical empty candidate instead of promoting it or silently selecting older bytes. A nonempty candidate that removes a required region or pin remains a parsed candidate; full Plan compilation must reject the resulting incomplete configuration and preserve the currently applied bundle. This separates an empty-source update failure from a nonempty-source policy incompatibility without allowing fallback.

`config.Store` gains only narrowly named immutable source-asset storage, under its existing writer flock and private root. Source files are addressed by SHA256 of their exact private `SensitiveAssetBytes` bytes. Publishing uses exclusive staging, file fsync, rename and parent fsync. It is not a source-success commit: only the associated operation result can make an asset latest/pending. Asset reads are bounded and read-only, check private ownership/mode/single-link/no-symlink and the content digest, and never repair a missing or corrupt file. A repeated identical publish must still establish a directory durability barrier after reopen.

Restoring a subscription Snapshot requires the original identity key and trusted local ParseOptions. The stored envelope is not authority: strictly decode it, re-parse its original provider bytes using the supplied source/key/region policy and compare the complete regenerated private asset bytes. Missing or changed key, metadata/region-policy tampering, parser-version drift and relabelled source IDs fail without a partial Snapshot. Normal query projections never include original provider bytes, URL secrets, credentials or keys.

## One journal, short writer sections

Use the existing operation Journal for `subscription.update`; do not introduce a mutable latest index that needs an unproved cross-file transaction with it. Before admitting the operation, publish a bounded immutable `source-update-context` asset containing schema1, operation/request identity, original active pointer, exact source definition, complete local region rules, settings digest, prepared-fetch digest, per-source sequence, and start/next-due times. The context contains neither URL-secret bytes nor the identity key. Its SHA becomes Journal.Intent.CandidateDigest and is retained in terminal public receipts, so compacting the request body does not discard the private input definition or declared region policy. A context orphan published before a failed admission is not an accepted attempt: no network worker starts until the Journal reservation is durable.

The private context uses exact Go JSON, maximum64KiB, valid absolute source references, the original ActivePointer shape, a sequence in1..2^53-1, and exact UTC RFC3339Nano timestamps. Enabled next_due must equal start+the validated whole-hour period; disabled updates carry null. It is a pure codec, not proof that the referenced settings, source, active pointer or operation exist.

The mutable operation receipt carries that context reference, bounded downloaded/validated/error state and any successfully validated provider-asset reference. Failure needs no additional immutable metadata file: its original context is already durable and its bounded result can retain the failed stage. Success/pending uses `data`; failure keeps `data:null` and the same bounded receipt in `error.details`, with fixed code `SUBSCRIPTION_UPDATE_FAILED` and no callback error text. The latest usable candidate, attempt time and next due are derived from validated receipts; current applied snapshot is derived independently from the active bundle. Compacted terminal results retain context/candidate references. Per-source sequence is allocated under the Coordinator lock from existing original receipts, not from wall-clock order or an untrusted provider value. Older successful operations remain the usable snapshot when a newer attempt fails; no mutable latest pointer is rolled back or silently cleared.

The finite update phases reuse the existing Journal transitions: prepared reserves the attempt; validated records that the frozen input passed admission; applying precedes FetchPrepared; verifying means the download completed and parsing is next; publishing references the durable parsed asset after input revalidation; committed alone exposes validated/latest. Publishing and committed retain the same completion timestamp and asset/snapshot identity. Any earlier ordinary failure goes through rolling_back to rolled_back with a bounded reason and no candidate reference; this does not undo a runtime mutation because the update never makes one. Uncertain Store errors stop further writes and retain the last durable phase for explicit recovery. Before publishing there is no usable candidate, including when parsing already produced an in-memory Snapshot. Phase receipts bind the context SHA, source ID, sequence, operation ID and base revision; readers validate their complete exact schema and binding, including compacted terminal records. Uncompacted histories require download_failed to originate at applying, validation_failed/storage_failed at verifying, and a downloaded flag change only at applying→verifying. Compacted records retain the terminal outcome assertion and input binding; they do not preserve independent step-by-step execution evidence. They never by themselves grant provider Snapshot authority, which still requires RestoreAsset with the original settings and region policy.

New requests first replay known identity, then validate exact params, expected global revision, source definition, local key/settings and pending/conflicting work. All pre-admission conflicts return without new durable state. There may be at most two live source updates and one per source across scheduled and explicit updates in the sole management service. Network download and provider parsing occur outside the configuration-application mutex. Brief reservation, receipt and asset publication steps hold the existing Coordinator writer boundary; Store mutexes only protect individual persistence calls.

Before any network request, durably admit the update and its attempt/next-due reservation. This consumes one attempted interval even if a crash prevents completion. Retry with the same request ID/body returns the original receipt and never starts a second fetch. A dead service's unfinished update is reported as interrupted/recovery-required; it cannot silently become zero attempts. Live downloads do not themselves authorize a runtime change. The exact admission/recovery phase evidence will be fixed in tests before the control handler is implemented.

The current service uses one synchronous request dispatcher. Therefore a network update cannot run synchronously inside dispatch: source-update admission returns a durable pending receipt, then a service-owned worker runs it under the service lifetime context. Losing or timing out the response does not start another worker on retry. Normal operation.get observes progress. The single source updater shares the existing coordinator lock only for short writer phases, bounds explicit and scheduled workers together, and cancels/joins workers before the coordinator closes its Store. Service-stop admission may cancel workers while holding the coordinator lock, but it must join them only after releasing that lock. The dispatcher and core apply state machine remain single-writer code.

The frozen download input binds the source definition, complete region policy, identity-key identity, settings identity and the exact private HTTPS URL/credential input. Fetch must consume that frozen input, not reread an unbound secret path between validation and request. Local file provider contents are the candidate being fetched, not a prerequisite that they stay unchanged from the previous update. At commit, recheck the source/settings identity and expected global revision under the writer lock. Changed identity produces a bounded stale/conflict outcome and cannot overwrite newer state; no provider body or private error chain is exposed.

The subscription layer provides `PrepareFetchSource(ctx, source)` and `FetchPrepared(ctx, prepared, options)`. Preparation validates a canonical absolute file/secret-reference path; for HTTPS it reads the bounded private secret once and freezes the normalized URL plus the exact original secret bytes in private owned memory. It performs no network request. Prepared input exposes a digest of a versioned exact definition/secret envelope and fixed redacted formatting, not the URL or body. For file sources only the definition is frozen; provider bytes are read during FetchPrepared and may legitimately differ from the previous candidate. A fresh preparation before commit must match the original digest. Identical secret bytes at the same reference are the same semantic input even if the filesystem inode changes; wholesale same-UID mutation is outside isolation. A prepared HTTPS fetch continues to use its original frozen URL if the reference changes or disappears, so a changed reference can never quietly redirect that in-flight request; commit-time revalidation still rejects the stale result. The existing standalone Fetch API keeps its prior caller-relative path semantics, while the service preparation boundary rejects relative paths rather than guessing a working directory.

Successful fetch is only Downloaded. Successful parsing creates a candidate; publish the immutable asset durably before recording a Publishing receipt that references it. Only a fully verified committed receipt makes it Latest/Validated. Pending is determined against the independently known Applied snapshot; a candidate equal to Applied does not fabricate a new application. Failure retains the previous usable snapshot and never clears a pin, switches supplier or replaces a running configuration. Orphaned immutable files from interrupted publication are not candidates merely because they exist.

Explicit recovery may finish a Publishing receipt only after rechecking the exact durable asset and original identity. Earlier interrupted fetch/validation is finalized as cancelled/interrupted without another network request. Recovery remains the existing `operation.recover` identity workflow, and queries never execute it. Service shutdown must cancel and join its update callbacks before releasing their writer lifetime; an old callback cannot publish after a new service acquires the lock.

Explicit source recovery performs bounded local RestoreAsset reproof under the existing recovery mutex, as other recovery proofs already do; it makes no network request. This is an exception to the live worker's parsing-outside-the-lock rule, not a latency guarantee for recovery. Admission/history reads and private secret preparation are also bounded local IO under the writer lock, not constant-time operations. A live source worker cannot be recovered concurrently. A dead source operation may be recovered independently of unrelated pending operations because it has no runtime effects; unrelated operations remain visible and unchanged. Both pre-admission and reconciliation verify the source context, and publishing/committed targets also require re-parsing the exact asset. Missing/corrupt assets are a read failure, never an automatic re-download. A publishing target whose current inputs changed is finalized as input_changed; pre-publishing targets become interrupted. Compacted terminal targets retain their historical outcome and can resolve an older interrupted recovery call without resurrecting the dropped request body.

## Read-only source inventory

`subscription.list` accepts `{}` or a single `cursor` string. Each page contains up to32 source rows sorted by source ID, full `total`, `view_id`, `revision`, observation time and an optional next cursor. The cursor binds active configuration, exact settings and all source journal record hashes plus live-worker state. Any change expires subsequent pages with SNAPSHOT_EXPIRED; queries do not retain or mutate a cursor store. Format/schema/unknown-field checks also apply to the opaque cursor. This bounded pagination does not silently discard sources that exceed one response frame.

Each row separates the latest attempt's downloaded/validated flags and error from the last successful candidate and independently applied snapshot. Latest and applied assets must both restore with their bound original key/region policy; absent/corrupt provenance fails the query, never becomes a missing/zero snapshot. Failed latest attempts retain the prior usable candidate. Pending compares a verified latest candidate to the applied bundle; downloading alone never claims application. Schedule enabled/hour values come only from committed Intent; an uncommitted optional Intent used for acquisition does not enable periodic updates. next_due still reports the durable last-attempt reservation and does not mean a timer has been started. Provider parsing for inventory happens outside the coordinator mutex on captured immutable bytes. No setting creation, fetch, recovery, cleanup or repair is permitted during a list or operation query.

effective_next_due is a separate read-only projection used by the service scheduler: when enabled, it preserves an existing reserved next_due; if a prior manual attempt did not reserve a period, it derives started_at plus the current committed interval. No previous attempt means immediate eligibility with a null effective time, rather than fabricating a historical timestamp. Disabled schedules report null effective_next_due while retaining their historical next_due. The service status's optional source_schedule describes the current process's timer only; offline queries never start a timer or restore this ephemeral status.

## Plan and Apply integration

An invalid source Plan returns no partial Plan. Its existing error envelope may contain `details.reason` and `details.field` for the first precise blocker: fixed reason codes distinguish missing selected/pinned nodes, required empty or unmatched-region groups, broken follow/source/app references, and unavailable local source snapshots. The field is a bounded logical location such as `groups[US].selected_node_id`, `rules[route].target` or `subscriptions[source-a]`; it never contains a provider display name, path, URL, endpoint, credential or parser error text. Source IDs and group/rule IDs are the caller's validated local identifiers. Missing or incompatible local candidates retain READ_UNAVAILABLE; invalid policy retains INVALID_ARGUMENT. Malformed input that cannot be safely classified keeps its generic error. This does not change exit classes, parser admission, Plan read-only behavior or fail-closed compilation. Complete aggregate diagnostics and the human config CLI remain later work; this first-blocker explanation is not a successful Plan with blockers hidden from Apply.

A strictly verified pending source update may coexist with Apply only while the sole updater still owns its original live worker. Both the first-runtime history guard and the shared Apply pending-operation guard use this narrow exception. A dead or malformed pending update still requires explicit recovery. After Apply releases the shared mutex, the worker must recheck its original full active pointer; an advanced revision produces input_changed without publishing the downloaded candidate. Other runtime operations retain their own existing admission requirements. The overlapping actual Apply/download case is included in the T043 finite acceptance; this is not a general concurrent-mutation claim.

The empty-runtime first-Apply guard also accepts strictly verified terminal source updates and completed recovery calls bound to those updates; they have no runtime effects. Arbitrary Journal records named subscription.update do not qualify. The original service-stop history proof remains unchanged. Source update terminal bodies may be compacted because their receipt retains the context binding. Recovery-call bodies targeting source updates are retained until reference-aware retention exists: their target operation link is needed to prove that they were configuration-neutral history. A compacted recovery call does not acquire such authority by guessing its target from a request digest.

Pure local Plan loads and validates only existing local inputs. It uses the existing source compiler and complete Plan binding, preserving stable group/follow selection and exact source/node pins. Runtime endpoint/credential inputs also require a commitment: derive the target generation from canonical Intent, compiler/capability/binary identity, exact source/rule assets and private runtime settings. This prevents a settings change from producing a different configuration under an unchanged approved Plan. The generation calculation excludes its own generated snapshot to avoid circular hashing.

Apply must re-read/recheck these local identities inside the existing US5 admission boundary, then use the original `BasicApplier` operation/publication/recovery sequence. Missing local assets do not trigger a download or re-plan. Materializing a private workdir is an explicit post-validation write, never a side effect of Plan or status, and cannot occur before stale revision/input checks. Supporting source compilation does not loosen the pinned ELF, original-process, closed-start or complete snapshot gates. A successful download or candidate compile never advances global revision.

The pure generation helper first compiles with a fixed discovery generation to obtain the complete referenced provider/rule/core/capability input set. It hashes a versioned envelope of canonical Intent, compiler version, capability digest, deterministically sorted inputs and the typed private settings digest, then compiles the final generation. Unreferenced provider map entries are not dependencies. It performs no filesystem reads and does not replace actual executable admission or same-key/source asset restoration by its caller.

The implemented workdir integration extends the existing BasicApplier rather than creating a separate runtime workflow. After complete new-request/revision/input/consent checks, it must validate generated material and the fixed executable, prove the previous runtime state and check operation capacity before making a preparation write. It then publishes an immutable private workdir-intent asset containing the random workdir name, original request/Plan identity and config digest, creates that fresh directory through PrepareLaunchWorkdir, and runs the ordinary full material/workdir checks before the existing bundle publication and Journal admission. The workdir-intent is a durable name record, not permission to launch and not an accepted operation. Interrupted preparation may leave an unreferenced workdir/asset; neither is adopted or erased by a retry/query. No runtime effect occurs until the original operation is admitted. This preserves the old read-only material source contract: preparation writes belong to the trusted applier after validation. The existing launcher still requires the complete workdir/config/executable checks, durable RunIntent and one-use launch ticket. T043 validates preparation interruption boundaries and actual first-start/running replacement using this path; it does not establish physical power-loss or arbitrary stopped-generation Apply behavior.

## Acceptance boundary and remaining matrix

The current finite source Plan profile explicitly rejects same-generation no-change plans and replacement of an already-stopped historical generation with CAPABILITY_UNSUPPORTED. Supported source Apply actions are the first start and full replacement of a running configuration; the existing runtime.start can separately start a committed stopped bundle. These limits must remain visible in acceptance reports and do not establish full product completion.

T043 bounded acceptance covers immutable storage and read-only checks, real-key rehydration, durable reservation/replay and actual manager SIGKILL without duplicate fetch, cancellation/join, source/secret/revision changes during fetch, shared worker limits, state separation, service/CLI list/update and actual source Plan/Apply through US5. See the linked validation document and per-run receipts for synthetic versus actual boundaries. T044 separately runs the complete two-source US/JP/BEST and failure matrix, including the minimal precise blocking reasons required by FR-015. Other platforms and performance/suspend claims remain unverified by T043.
