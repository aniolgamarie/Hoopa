# 组合原型、阶段计划与验收

本项目当前处于 P0 实施阶段，已有[隔离实验工具](../experiments/gost-mihomo/README.md)。受控收发及真实 Codex 接入已有初步证据，其他门槛须逐项验证。本文定义完整验收要求，不代表下列场景全部通过；具体状态见[任务记录](task-log.md)。

实测后按[ADR 005](adr/005-telemetry-replan.md)重规划：下文GOST→Mihomo链保留为历史校准/兼容对照；完整进程计量与质量来源改为同一Mihomo数据面候选。接收journal已实测重开20条已送达事件，来源未送达/进程权限/计时与线路仍待验证，不改原故障分母或P0门槛。

## 1. P0 的输入与最小产物

优先 Linux。固定一个实际使用的 Agent CLI 作为目标应用，记录名称、版本、启动方式和支持的代理变量；`curl` 等小工具用于可控流量校准，不单独替代目标应用验收。目标应用尚未选定不阻止先做本地 TCP 校准，但不能据此关闭真实应用门槛。

原型执行前准备：

- 明确路径的 Mihomo、GOST v3 二进制和 SHA-256、版本输出、对应源码 tag/commit；不要使用可变的 `latest` 或自动升级。
- 一份合法可用的测试订阅、测试节点或受控代理端；至少有两份可区分的供应商数据，以及缺 US/JP、重复节点名、无效 YAML 等合成 fixtures。
- 一个可控 HTTP/TCP 服务，提供固定数据、慢速响应、上传、长连接和错误响应；可控失败与真实网络两类环境分别记录。
- 独立用户私有实验目录和未占用的 loopback 端口；不修改现有代理、父 shell 或系统设置。
- 故障注入脚本只操作实验实例的已验证身份，不能按进程名全局 kill。

`experiments/gost-mihomo/` 已建立，内容限定为最小配置模板、启动/采集 harness、受控端点、断言和脱敏结果。不要在 P0 实现完整配置 schema、全部 Cobra 命令、完整 TUI 或报表系统。

一次执行至少生成如下证据：

```text
evidence/<run-id>/
  manifest.json             OS/架构、工具版本与摘要、应用版本、配置摘要、时间
  events.jsonl              启动、采样、故障、重启、接管、恢复的顺序
  metrics-before.txt        脱敏后的原始指标与完整标签
  metrics-after.txt
  connections.jsonl         长连接是否中断、是否重新连入、出站身份
  ledger-check.json         checkpoint/delta/gap 的前后结果
  result.md                 断言、观察、未验证项、通过/失败与决策
```

不把完整订阅、认证配置、应用 prompt 或真实请求内容提交到 Git。原始敏感证据留在私有目录；可复现的合成 fixtures 与脱敏摘要才进入仓库。

## 2. 最短端到端路径

先验证 TCP，候选端口为实验值，不是产品默认端口：

```text
目标应用
  HTTP_PROXY / HTTPS_PROXY = http://127.0.0.1:18080
        ↓
GOST app-one HTTP/TCP service        127.0.0.1:18080
  metrics                           127.0.0.1:19000
  forwarding chain: SOCKS5/TCP
        ↓
Mihomo mixed 入站                    127.0.0.1:17890
  私有 controller + secret
  本地规则 + 本地节点 provider
        ↓
受控目标与真实业务网络
```

以下是结构示意；实际已运行的[实验模板](../experiments/gost-mihomo/gost.yaml)包含独立认证与随机端口。其他版本仍须重新核验，不能把本示意直接用于受保护的实验：

```yaml
services:
  - name: app-one
    addr: 127.0.0.1:18080
    handler:
      type: http
      chain: mihomo
    listener:
      type: tcp
chains:
  - name: mihomo
    hops:
      - name: hop-0
        nodes:
          - name: mihomo-socks
            addr: 127.0.0.1:17890
            connector:
              type: socks5
            dialer:
              type: tcp
metrics:
  addr: 127.0.0.1:19000
```

这是实验模板，正式实现还需加入随机且可追溯的 service 身份、本地访问保护和运行登记。GOST 与 Mihomo 均只绑定 loopback；controller 凭据不写入该示例。验证 SOCKS5 入口时另建案例，不假定换一个 handler 就覆盖全部应用。

按以下顺序推进，每步都有可观察结果：

1. **建立对照**：应用直接使用共享 Mihomo 正常联网；再经 GOST 联网，确认实际出口和规则命中相同，排除代理变量被忽略、NO_PROXY 或本地配置绕过。
2. **解释计数**：固定大小上传/下载、HTTP CONNECT、SOCKS5、失败重试、并发与长连接，记录入口 counter 原始值。拆分应用净数据、握手与协议开销；对可控 TCP 路径给出明确参照，禁止用任意百分比容差掩盖无法解释的差异。
3. **确认指标结构**：确认 `host/service/client` 标签、按 series 做差后仅汇总一次、序列保留与数值格式；所查源码不提供独立 service 总量，不预设存在父级序列。活跃长连接持续采样，不等连接关闭再判断计数。
4. **重载与重启实验**：分别改变 GOST service、metrics 配置和 Mihomo 配置；区分 exporter 可达性、counter 是否延续、旧连接是否存活、新连接实际路径。只测试固定版本确实支持的 reload 入口，不假设 SIGHUP 一定可用。
5. **进程存活与接管**：脱离终端启动，关闭 TUI/CLI、退出 SSH、杀死管理器，再用身份记录接管。分别记录代理连续性和采集连续性。
6. **验证严格切换启动**：Mihomo 仅 controller 启动 → 本地 provider 就绪 → 选择及拒绝回退核验 → 开放 mixed 入口。持续并发连接验证全过程只能看到旧快照、新快照或失败，不出现混合配置或缺组直连。
7. **最小账本探针**：对同一样本重放、事务中断、磁盘失败、新世代和无法解释的归零建立可执行断言。此时只验证 checkpoint/delta/gap 关键路径，不实现完整历史面板。
8. **实际应用验收**：用固定的真实 Agent CLI 完成正常工作流与持续连接工作流，验证 wrapper 信号、退出状态与计量开关；应用有后台进程时记录旧入口保留行为。
9. **进程与域名事实探针**：至少两个同名进程并发并访问不同域名，覆盖各自发起连接的子进程、后台后代、短于采样周期的连接、PID 复用和仅 IP 目标；证明源 PID/进程名、目标证据及终末字节能保留并与入口量对账。验证采集停机后明细重放，不能仅凭 GOST 总量或 Mihomo 活动快照通过。探针不提前实现完整查询面板，详细要求见[流量统计](traffic-statistics.md)。
10. **连接质量探针**：记录可验证的转发建立/首响应起止事件、尝试与结果，覆盖慢请求、慢响应、超时、复用、HTTPS 不可见与采集缺口；验证节点 probe 不冒充业务时延、固定窗口流量不插值，以及实际连接链跨选组切换的历史关联。
11. **应用与进程规则探针**：无 GOST/数据库时，两个 profile 通过命名入站选择不同组/固定节点，校验应用/域名规则顺序及实际链。进程规则按 `basis=connect_initiator_v1` 验证 connect 发起 PID/启动实例与名称/路径建连快照，在选路前证明其与原 accepted socket 关联；名称和路径能力分别加载校验，所需字段 unknown 按三态拒绝。另测固定目标失效和管理器崩溃后策略继续执行；不能仅靠事后识别 PID 宣称实时进程路由可行。

## 3. 必须执行的故障矩阵

| 编号 | 故障或操作 | 必须观察到的结果 |
| --- | --- | --- |
| F01 | 退出 CLI / TUI | Mihomo/GOST 仍按预期转发，界面进程不托管连接 |
| F02 | `SIGKILL` 管理器或平台等价操作 | 旧长连接与新连接继续性分别记录；采集暂停不能显示成零 |
| F03 | 重启管理器并接管 | 不重复启动核心、不重建 GOST epoch；从 checkpoint 补差且无重复 |
| F04 | SSH 断开、用户注销、系统休眠恢复 | 分别记录，不能用关闭终端代替；恢复后到期任务每订阅最多补一次 |
| F05 | 采集工作循环失败或 metrics 不可达 | 转发继续，状态 stale；同一世代恢复后补回累计，时间分布注明未知 |
| F06 | GOST 被杀、Mihomo 被杀 | 区分受影响入口；不偷偷绕过 GOST 或直连；重启有新进程身份，未知尾段入 gap |
| F07 | SQLite 写失败与事务中断 | checkpoint/delta 同进退；恢复重试不重计，不能依赖仅内存状态 |
| F08 | 下载失败、空 provider、节点消失 | 保留旧快照；明确组缺失，不自动直连、不换供应商 |
| F09 | 某一必需组默认选择不存在 | 不接受“自动首节点”作为手选成功；入口保持关闭或整次回滚 |
| F10 | 新配置检查成功但绑定失败 | 候选退出后恢复完整旧配置；不能让旧、新进程争用端口 |
| F11 | apply 中每个持久化边界杀死管理器 | 重启能识别 prepared/applying/verified/committed 状态并确定恢复；无法确定时报 degraded |
| F12 | 运行态应用成功、active 指针写入失败 | 返回失败/不确定而非成功；持久操作记录足以在恢复时消歧 |
| F13 | 回滚也失败 | 暴露 degraded、保留新旧证据，停止自动写操作，不假报已恢复 |
| F14 | PID 复用、端口被外部进程占用、记录缺失 | 不错误接管、不杀外部进程、不默认另起核心 |
| F15 | 计量开/关、配置 revision 变化 | 新启动使用新入口；旧进程继续旧入口；不自动重启应用或伪称连接迁移 |
| F16 | 服务同名重建、counter 归零、series 消失 | 明确新 epoch 或异常，旧 checkpoint 不跨身份相减 |
| F17 | 仅运行 status / doctor | 在时钟与后台任务受控的对照环境比较文件树、hash、mtime 与进程集合，查询不得引发变化；不更新/探测/迁移。atime 与无关后台写入单列，避免误判因果 |
| F18 | 基础环境没有 GOST / 没有数据库 | 不计量的订阅管理、路由、接入与只读诊断仍正常 |
| F19 | managed/inherit/direct 的代理环境冲突 | 仅目标子进程受影响；managed 不静默降级；direct 不承诺绕过 TUN |
| F20 | 同名 connector 并发、退出后 PID 被复用或 exec/改名 | 保留 connect 发起 PID/启动实例与建连名称/路径快照；历史不串账，同名合并可展开各实例，合并前后总量一致 |
| F21 | 子进程自己 connect、父 connect 后子写、fork 共享/FD 转交、wrapper 退出或 GOST 对照 | 子 connect 归子、父 connect 后子写归有真实证据的父 connector；共享/转交不改归属、不自动 unknown；profile/launcher/GOST 不替代 connector；始终显示口径、观测时点和限制，未监测转交显示 `fd_transfer_observation=unverified` |
| F22 | 极短连接、突发并发、管理器停采 | 受控场景的终末字节与维度事实不因快照漏采而消失；不能恢复时标维度/字节缺口，不能宣称完整 |
| F23 | 多域名共 IP、单域名多 IP、仅 IP/加密不可见或连接复用 | 有证据的完整主机名正确分组；IP 和未知桶保留；不可分段的连接不复制到多个域名 |
| F24 | 入口与连接层计数边界或截止点不同 | 显示 pending/not_comparable；同口径对齐后按方向对账；不比例摊分、不将负差额截成零 |
| F25 | 同名合并、进程/域名交叉筛选、排序分页与 Top N | 同一数据版本下升降序稳定、PID 实例可下钻；隐藏项/未知项保留总计，维度总数不相加 |
| F26 | 慢业务、probe 很快、超时/失败、复用与 HTTPS 不可见 | 按定义区分建立/首字节/probe，缺样 N/A；失败与超时单列，不填零、不用连接存活时间作延迟 |
| F27 | 多进程 p95 合并、采样缺口、不同窗口流量与速率 | 从同口径样本/兼容直方图重算分位数；同窗口先汇总字节再算速率，不平均 p95/行速率，不补造逐秒曲线 |
| F28 | 自动组选组切换、节点改名、一个进程多条不同线路 | 保存原连接实际节点/来源/链及世代，不用当前 now 回填；汇总能展开节点分布和样本质量 |
| F29 | 应用规则指定组/固定节点且未安装 GOST/SQLite | 专属 Mihomo 入站可保留应用上下文，应用实际路径正确，基础应用选路不依赖计量 |
| F30 | connector 不明、事件丢失、后端 generation 不符、原 socket 关联多解、字段缺失或身份晚到 | 共享/转交本身不否定已验证 connector；所需身份字段 unknown 按三态拒绝且原因可见；不以 GOST/profile/launcher 或默认父身份填补；未支持 name/path 分别加载拒绝，统计晚到补证不改写过去选路 |
| F31 | 应用/进程/域名/IP 规则有重叠或遮蔽 | 按显式顺序首个确定匹配，plan 解释遮蔽；不以隐式更具体优先改变规则，面板查询不触发 probe/改选 |
| F32 | 目标组为空、固定节点被删/不可达，或切换活动订阅 | 无效候选拒绝并保留旧快照；固定 provider+node pin 不重绑定，所有引用来源均校验；不可达不偷偷换节点、供应商或直连 |
| F33 | 应用入站部分绑定失败、管理器在路由应用/运行中崩溃 | 复用完整快照回滚并验证全部入站；已应用转发策略不逐连接依赖管理器在线 RPC，存活/接管行为有证据 |

F11 的注入点包括候选落盘、写 applying、旧进程退出、新进程登记、选择核验、开放端口、发布 active 和提交记录。控制面文件操作与 SQLite 事务分别覆盖，不能用一类测试代替另一类。

F20/F21/F30 以上为 connector 口径下的新验收预期，尚须单独执行并记录；原严格验收 0/100 的失败结果与分母保持不变，不据新口径追认通过。此口径记录连接发起实例，不承诺识别逐字节 writer 或自动探测全部 FD 转交。

T134 另须覆盖 HTTP CONNECT 成功回复与首段 application payload 同包到达的场景：回复解析保留后续 payload，转发不丢字节，计量按既定边界只计一次。此项是待验要求，尚无已证新 bug 或通过结论；与 SOCKS5 回复头校验的局部补丁证据分别记录。

## 4. P0 退出门槛

必须有 Linux 实际运行证据证明真实应用链路、入口字节语义、世代识别、管理器崩溃与接管、采集降级、部分应用回滚以及分阶段启动的边界。新增的源 PID/进程名、可观察域名、短连接终末值与对账探针也必须证明采集可行性；当前接口若不足，需先调整适配设计。影响关键保证的失败由主代理决策，不能以增加 CLI/TUI 功能或仅展示入口总量绕开。

延迟/窗口流量/实际节点和[应用与进程路由](routing.md)还须证明采集与执行时序：计时事件真实可见，路由前取得所需身份，无 GOST 时应用规则可用，原连接链与当前组选择可区分。P0 只做最小探针及方案裁决，完整排序、质量历史和规则编辑仍按 P1/P2 交付。

计量开关首期建议采用“只影响后续启动”，仍要证明旧入口保留、端口冲突、wrapper 崩溃与长连接结果后才能定稿。GOST reload 失败不必阻止采用不可变入口实现，只要该基线的生命周期门槛通过，并明确不支持的热修改范围。

SQLite 驱动实验至少比较一个纯 Go 候选与一个 CGO 候选：固定版本、同一测试集、跨平台构建难度、崩溃恢复、busy 行为、只读访问、二进制与内存开销。驱动未选定可以继续不依赖账本的 P1；计数连续性与不可恢复缺口的语义不能后补。

没有真实平台、核心二进制、订阅或应用时，记录“环境不足未验证”并列出缺失输入。没有执行的命令不能记录通过。停止在设计阶段不意味着 P0 或全项目完成。

## 5. 分阶段交付

| 阶段 | 交付范围 | 完成判据 |
| --- | --- | --- |
| P0 组合原型 | 真实应用、GOST/Mihomo、最小进程/计量/事务探针 | 上述关键链路与故障证据齐全，设计门槛有裁决 |
| P1 独立基础管理 | 订阅、本地有序规则、稳定组、应用指定组/节点、更新调度、三种接入模式、status/doctor、JSON v1 | 无 GOST / 无 SQLite 可用，应用入站保持上下文；缺目标失败关闭、快照保留和严格切换通过 |
| P2 可靠计量与界面 | 事实账本、进程/域名交叉查询、真实源进程路由、延迟/窗口流量/实际节点、同名合并、排序、缺口与按需 TUI | 源身份及时可用，短连接历史、对账、质量口径/覆盖、实际链、故障恢复及查询通过；不能仅以总量可用判完成 |
| P3 平台验收与迁移 | macOS/Windows 适用 CI、实际平台生命周期、旧工具迁移 | 每个平台的支持范围有证据；迁移可预览、备份、回退，不默认启用全局代理 |

P1 完成只代表基础管理可用，不能标记整项目完成。P3 迁移先读取和预览旧工具配置，用户明确执行后才替换；迁移前不抢占旧端口、不删旧配置。

P1 的用户流程验收还包括[功能规划](features.md)中的四项：首次配置引导、区分静态与实际证据的路由解释、切换影响预览、仅针对目标子进程的应用接入预览。分别覆盖缺少核心或必需地区、规则信息不足、手选失效及中断提示、代理变量冲突和 NO_PROXY；这些流程不能要求先安装 GOST、创建账本或打开 TUI。此补充不改变 P0 组合原型优先的实施顺序。

## 6. 性能目标与平台边界

以下是待校验目标，不是测量结果：

| 项目 | 目标 | 统一测量口径 |
| --- | --- | --- |
| 管理器空闲 RSS | ≤ 40 MiB | 不打开 TUI，固定订阅与规则规模，说明采集是否启用 |
| 管理器平均 CPU | 10 分钟平均 < 单核 0.5% | 进程 CPU 时间差 / 600 秒，不取单次 top 瞬时值 |
| 整套空闲内存 | ≤ 200 MiB | Hoopa + Mihomo + GOST 总和；分别测 0、1、5 个计量入口，列出 RSS 与可用时的 PSS |
| Hoopa 压缩包 | ≤ 10 MiB | 首期按仅含 Hoopa 的发行包测量，外部核心分列；此口径在基线时确认 |
| Hoopa 二进制 | ≤ 25 MiB | 记录 OS/架构、构建参数、是否含 TUI 和 SQLite 驱动 |

同时保存冷启动、配置切换中断时长、订阅更新峰值、账本增长速度与采集周期。样本规模包括节点数、规则数、应用入口数和日志等级，不以空配置代表实际使用。

计量样本额外记录并发 launch/进程数、域名与连接基数、短连接速率、归属证据方式、明细保留期，以及进程/域名排序与交叉查询耗时。低内存目标不能通过丢弃受承诺的明细或只保存活动连接来达成。

Linux 先本机验收。macOS/Windows 的编译、单元测试、适用的本地回环集成使用标准托管 CI，不使用额外付费的大规格 runner。公开仓库标准 runner 的免费政策与私有仓库配额不同，见[开发规范](development.md)；“标准托管”本身不保证任意仓库都零费用。

CI 通过不等于 SSH/休眠/注销行为通过。支持表分别列构建、回环集成、真实应用、退出/休眠和性能；没有真实运行证据的平台标为未验证或实验性，不能只凭 GOOS 交叉编译宣称正式支持。
