# 应用入口计量与历史账本

状态：实测后重规划，依据[ADR 005](adr/005-telemetry-replan.md)。完整计量改用同一数据面事件候选；下文GOST指标部分保留为兼容/累计对照，不再作为完整进程账本的默认来源。生产事务与完整源能力待验证。

## 1. 计量对象与入口生命周期

计量对象是 **经过Hoopa已验证入口、具有明确计数边界的字节**。完整统计候选采用待校准的Mihomo代理转发流边界；旧GOST入口原始字节分源保存，不改写历史或混算。它不是模型 Token 数、供应商账单、真实公网链路字节或整机审计；不保证发现绕过该入口的请求。首期只承诺实际验收通过的 TCP 场景，不宣称完整 UDP / QUIC 覆盖。

P2 必须在该范围内提供进程（含 PID、进程名）、域名及交叉查询，同名合并和排序；入口累计只是对账基础，不能单独代表明细完整。字段、查询、身份及采集门槛见[进程与域名统计](traffic-statistics.md)。

不计量managed应用使用共享或应用专属Mihomo入站。完整计量候选直接进入具备已验证事件能力的Mihomo，保留原始socket并关联计数/实际链；GOST入口仅保留兼容和累计对照。入口绑定app与配置世代，launch通过可验证入站/认证或原进程登记关联；不能从共享profile推导launch，无法证明时标launch_unknown。新增入口的plan/apply与排空须先验收，不因每次run隐式重载。规则顺序与身份门槛见[路由设计](routing.md)。

这里的“应用”是 Hoopa profile，不是 OS 强制隔离身份。独立 launch 入口只能证明启动上下文，不能把主进程 PID 自动赋给全部子进程；真实源进程按原始 TCP connect 发起实例（connector）记录，须从建连事件及其与原 accepted socket 的关联取得证据。知道端口或凭据的其他进程也可能使用入口，不能根据 metrics 的 `client` IP 标签反推出 Agent 身份。loopback 绑定和可用的本地认证降低误接入，不构成同一用户下的安全隔离。同名汇总在查询时完成，原始实例记录保留。

默认口径为 `basis=connect_initiator_v1`：子进程自己 connect 归子，父 connect 后子写归父 connector；FD 转交、fork 共享和写入者变化不重写连接归属，也不因共享本身记 unknown。名称/路径保存建连快照及来源，路由前验证快照关联；connector 不明、事件丢失、后端 generation 不符或关联多解才保留未知原因。展示口径、观测时点与共享转交限制；未监测转交则显示 `fd_transfer_observation=unverified`，不表示已识别逐字节 writer。

| 变更 | 首期行为 | 现有进程与长连接 |
| --- | --- | --- |
| 不计量 → 计量 | 后续 launch 创建对应计量入口，不与并发 launch 混用 | 现有环境不变，继续走共享入口，不追溯计量 |
| 计量 → 不计量 | 后续 launch 改为对应 Mihomo 入口，保留定向规则所需上下文 | 旧入口继续保留，旧进程仍被计量至自然结束或显式停止 |
| 计量 → 修改入口配置 | 创建新入口 revision，旧入口退役待排空 | 不在存量 GOST 上隐式重载以求“无缝” |
| 重启应用 | 由用户或调用方显式执行 | 重新获取入口；已有连接不迁移 |

配置响应显示 `applies_to: future_launches` 和仍使用旧 revision 的运行记录。端口不承诺在两种模式间相同；在一个入口存活期间保持稳定，进程恢复或地址冲突须报告实际地址。agentcfg 每次启动前解析入口，不把端口写死在自己的配置中。

`launch_id` 是一次启动记录，`endpoint_id` 是应用入口，`service_id` 是 Hoopa 分配的不可复用服务身份。子进程退出不证明后台后代或外部使用者全部退出；wrapper 崩溃也会留下未知 lease。此时保留入口并标记 `draining/ownership_unknown`，不能仅靠 TTL 或零活跃连接快照自动杀死仍可能再次发起连接的应用。显式清理命令说明中断影响，结束入口前尽力执行终末采样。

## 2. GOST累计对照与数据质量

GOST 文档中的字节 counter 为 `gost_service_transfer_input_bytes_total` 与 `gost_service_transfer_output_bytes_total`，分别表示服务接收与发送字节。标签和 TCP 包装源码的定向核查见[上游资料](references.md)。输入/输出以入口服务视角命名；UI 在选定协议验证方向后才标注上传/下载。

GOST兼容入口累计从metrics采集，不额外部署Prometheus；完整统计则要求ADR 005的同源事件。接收journal的Write+Sync/去重/重开已可实验，但不是完整来源。API stats/observer是不同候选，不能混用或重复累计。进程/域名维度需要另外验证连接级事实采集，不能假定 metrics 自带这些维度、将名为 host 的指标标签直接当作业务目标域名，或用 Mihomo 的活动连接轮询补出完整历史。采集器使用标准指标解析方式，不能用按空格切分的临时脚本作为正式实现。

采样规则：

1. 从受保护的运行登记中获取进程身份、入口映射与 metrics 地址，不从任意同名服务接受数据。
2. 精确匹配允许的 service 与指标族，保留完整 series 标签指纹。所查源码只有带 client 的字节 counter：对每个完整 series 各自计算 delta，再按 host/service 汇总一次；不能把另行计算的聚合值再次加入分项。固定版本原型冻结实际标签，出现未支持结构时报告不兼容。首次出现的 series 只有在可证明从零开始时才从零起算，未出现指标不等于存在一个零值基线。
3. 不把指标缺失、标签消失、HTTP 错误、解析失败或 NaN / Inf 当成数值 0。不以总和掩盖某一个 series 的归零。
4. 保存原始导出数值或其可审计表示。确认导出精度、最大值与 SQLite 整数边界，禁止用 Go 的平台相关 `int` 存累计字节。如果导出浮点 counter 超出逐字节精度范围，标注精度限制；不能先四舍五入再宣称严格字节精确。
5. 入口 TCP 数据可能包括代理握手、应用协议头和加密数据，不能要求 counter 与下载文件净长度无条件相等。P0 先量出计数边界，建立可解释的参照。

## 3. 世代与检查点

区分以下身份：

- `manager_run_id`：Hoopa 管理服务本次运行，仅用于诊断；管理器重启不创建新的数据计数世代。
- `process_run_id`：经OS身份校验的计数来源进程世代（完整候选Mihomo或兼容GOST）；不代表业务源进程。
- `source_process_instance_id`：原始 TCP connector 实例，保存 connect 发起 PID、OS 启动身份与建连名称/路径快照，主进程和子进程分别记录，不能仅按 PID 去重或用 profile/launcher/GOST 身份替代。
- `service_id/service_revision`：入口业务身份与服务配置世代，不依赖可复用的显示名。
- `counter_epoch_id`：计数器连续且同源的一段生命周期；同一个进程内重载也可能产生新 epoch。
- `series_key`：固定版本适配器规范化后的指标名及完整标签集合。

检查点键为 `(process_run_id, service_id, counter_epoch_id, series_key)`。指标本身没有足够身份字段时，由运行登记绑定；不能通过数值“看起来接得上”决定接管。

同一已证明连续的 counter：上次 `C0=1000`，本次 `C1=1600`，提交差量 `600`。重试同一样本不再增加。若本次变为 `100`，不能计算 `-900`，也不能直接当作又产生了 `100`；先判断是已知新世代、未声明归零还是错连服务。

已知新进程从零启动，且证明开始接流量前基线为零时，第一次 counter 可以作为该世代差量。接管现存进程且无可恢复检查点时，第一次值只建立基线，启动至基线之间标记归属不明或缺口，不能默默补进历史。未知重置时封存旧 epoch，标注不确定区间，再从可信基线开始。

GOST 兼容对照入口的首次启动顺序为：准备登记与私有配置 → 启动 GOST → 校验服务身份和初始计数 → 建立检查点 → 将入口提供给 launch。完整候选的 Mihomo 事件入口仍须单独验收身份、来源世代及检查点就绪边界。若启动过程中已出现非零计数，必须解释其来源，不能假定这一段全属于待启动的应用。

## 4. SQLite 事务边界

建议的逻辑表如下；入口账和维度事实分别建模，具体 DDL、驱动与迁移在 P0 的驱动探针及 P2 实现时定稿。

| 表 | 关键内容 |
| --- | --- |
| `service_runs` | app / endpoint / process / service / epoch 身份、开始结束、来源版本 |
| `checkpoints` | 每个 series 的最近 counter、sample ID、时间、事务序号 |
| `usage_deltas` | 入口上下文身份、前后 sample、字节增量、采样区间、计数边界与质量标记 |
| `source_processes` | connector 实例、connect 发起 PID/启动身份、建连名称/路径/用户快照及证据来源 |
| `connections` | 源连接及转发关联、目标域名/IP、元数据来源、生命周期与关闭状态 |
| `connection_checkpoints` / `traffic_facts` | 每个连接世代的已确认位置与增量事实，含进程/域名关联与计数口径 |
| `attribution_revisions` | 晚到 connector 归属补证、证据版本和对账状态，不重复插入字节或改写历史路由决定 |
| `quality_samples` / `connection_routes` | 去重的连接尝试/请求/探测时延样本及结果、实际节点/链、规则与配置世代；不叠加为流量 |
| `gaps` | 开始、结束或 open-ended、原因、字节/进程/域名受影响维度、恢复程度，不确定字节为 unknown |
| `schema_migrations` | 数据库版本与已完成迁移 |

每次采样使用短事务，采样 HTTP 请求和进程操作都在事务之外：

```text
验证运行身份与样本
BEGIN
  读取该 epoch/series 的 checkpoint
  核对样本顺序和连续性；计算 delta 或生成缺口事件
  插入 usage_delta（sample ID / 前后序号有唯一约束）
  更新 checkpoint（与 delta 同一事务）
  插入或更新 gap / epoch 状态
COMMIT
提交成功后才更新内存中的已确认位置
```

单采集写入者配合唯一约束和预期 checkpoint 版本，防止重试或误启动第二个采集器重复记账。明确字节上界，溢出在提交前拒绝并暴露质量异常，不用浮点存历史总额。UTC 时间用于展示，样本次序与世代身份用于去重；墙钟回拨不能重复累计。

连接检查点和连接增量事实同样在同一短事务提交；进程、域名及同名汇总从同一份事实投影，不能把多个维度的总数再相加。入口与连接采集源各自有恢复边界，只有口径、世代和截止点对齐后才对账，未对齐或不可比较须明确显示，不能按比例分摊入口总量。详细规则见[统计设计](traffic-statistics.md)。

不把内存中提前推进的位置写入下一次采样。事务中途进程退出、磁盘满或 COMMIT 返回不确定时，重新打开后以数据库中同一 sample ID 与 checkpoint 判定结果，再重试；不能看到超时就盲目再加一次。SQLite journal mode、同步级别、busy timeout、迁移锁和备份恢复必须写入驱动实验结果，不仅测试普通插入。

历史桶不能伪装成精确时间分布。停采后读到的累计差量覆盖整个采样区间；跨小时的差量保存原区间，小时汇总需标为估算，或显示为跨桶未分配数值，不能全塞进恢复后的某一分钟。账本维护采用显式命令与保留策略，不能每条数据永久增长而不计磁盘开销。

## 5. 故障与缺口

| 场景 | 转发 | 账本处理与状态 |
| --- | --- | --- |
| 采集器暂时失败、GOST 同一世代仍存活 | 继续 | `stale`；同源 counter 可补回入口累计，时间分布未知；进程/域名明细是否可补另看持久连接证据，不能由总量推导 |
| 管理器崩溃，Mihomo/GOST 存活 | 目标为继续，P0 必须验收 | 接管身份后从持久 checkpoint 补入口差，不新建 epoch；无法重放的维度事实记明细缺口 |
| GOST 在最后采样后崩溃 | 该入口失效，不暗中改走共享入口 | 上次采样到退出之间尾段未知，记永久 gap；新进程使用新 epoch |
| metrics 不可访问而代理可用 | 继续 | 显示计量不可用，不显示零流量 |
| 数据库写失败 | 已有转发继续 | 不推进 checkpoint；同世代恢复后可补差。若其间 GOST 也退出，记录无法恢复的尾段 |
| 新计量入口初始检查点无法持久化 | 默认拒绝计量 launch | 用户可显式选择“不计量启动”，必须成为可见的新模式选择，不能自动降级 |
| counter 无法解释地下降或 series 缺失 | 不因计量故障改路 | 冻结受影响 epoch，标质量异常与不确定区间，不记负值 |
| 应用重试了失败请求 | 由应用决定 | 入口实际经过的字节都可能计入，不按成功响应去重 |

`usage` 响应区分 `observed_bytes`、覆盖区间、最后样本时间、open gaps、permanent gaps、进程/域名归属覆盖率和对账状态，以及精度/时间分配质量。已知累计、缺口和实时速率分别表达；即便已知值为 0，也同时保留未知区间。元数据、已退出进程和成功账本样本不应被短期连接缓存或日志轮转删除。

单位时间流量、访问延迟和节点质量沿用[统计设计](traffic-statistics.md)的窗口、测量定义与实际线路证据。入口 counter 只能提供字节增量，不能据此生成 DNS/TLS/首字节耗时。质量样本、错误/超时和路由快照独立去重并关联原连接；停采后能补字节不代表能补回逐秒速率、延迟或实际节点历史。

status / doctor 优先读取管理服务已发布的计量快照。服务不在时，仅在能证明不创建、迁移、回放或写入 journal 的模式下读取现有账本；否则返回 `ledger_unavailable` 及最后持久状态。不能对仍写入的 WAL 数据库使用 `immutable=1` 来强行获取只读结果。迁移、修复与强一致历史查询是单独显式操作。

## 6. 不能提前承诺的行为

P0 必须给出：目标应用实际遵守的代理协议、HTTP CONNECT/SOCKS5 的计数边界、活跃长连接下的采样可见性、GOST reload/restart 的归零边界、指标缺失含义、计量开关与旧入口排空、重试幂等，以及采集失败后恢复的覆盖程度。

新增的 P0 门槛包括真实源进程 PID/名称、子进程归属、可观察域名、短连接终末值，以及入口/连接口径对账。现有组合若不能提供这些证据，需主代理调整采集适配方案，不能把缺口伪装为完整统计。

完整历史账本、进程/域名视图、同名合并、交叉筛选与排序属于 P2 必需能力；P0 只做最小事实、身份关联和 checkpoint/delta 探针，不提前实现所有报表。性能预算同时测一个入口和多个并发 launch 入口，若独立 GOST 进程使预算不可达，再据实决定共享服务模型；不能为了达到预算跳过身份、世代或维度完整性。
